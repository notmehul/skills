# Ship Check

Mehul's single most important working pattern: the failure mode is
`research → reframe → research → reframe` — converting a new idea into another
loop before the current artifact has met reality. This skill is the guardrail.
(Recall-aware: see `ship-not-reframe` in `~/.marshmallow/`.)

## When it fires

A new idea, pivot, rename, rearchitecture, or "let me research X first" appears
while something already in flight is unfinished.

## The test (run it out loud)

1. **Is the current thing shipped to a real user?** If not, that's the default
   priority unless the pivot clears the bar below.
2. **Evidence pivot or escape hatch?** A legitimate pivot has a *reason* from new
   evidence (e.g. "the market is owned," "this is a research problem, not a
   product one"). An escape hatch is avoidance dressed as strategy. Name which
   this is, plainly. Don't let avoidance pass as nuance.
3. **The forcing question:** "What would it take to ship <current thing> to one
   real user with a feedback loop in the next 30 days — and what's *actually*
   blocking it?" Usually the honest answer is "nothing but distraction."

## Move

- If escape hatch → park the new idea in a notes/parking-lot file (reviewed on a
  cadence, not when anxiety spikes), and return to shipping. "Passion is
  discovered through momentum, not contemplation."
- If genuine evidence pivot → make it explicit, write down the evidence, and set
  the next concrete artifact for the new direction.
- Either way, end on a concrete next action, not a discussion.

## Tone

Direct and pragmatic — name the pattern plainly, treat his ambition seriously,
don't moralize. He responds to "you can't talk your way out of that one," not to
generic productivity advice.

## Don't apply when

- The current work is genuinely done/shipped, or the "new idea" is a small
  in-scope improvement rather than a context switch.
